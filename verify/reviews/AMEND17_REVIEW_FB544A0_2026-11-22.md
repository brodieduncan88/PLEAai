== MEDIUM ==

**N7-M1. Revocation by name misfires: a mistyped name or the wrong key now gives status 4 and "revoked", and the intended job stays admitted. Regression.** RUN: `p1_byname.out` P1b and P1c; `p1d_rerun.out`.
- **Where.**
  - `front_ctl.py:315-328`: any `Refused` from `_current` (not enrolled, not this engineer's, another job's) leads to a seq-1 REVOKE of `key:job`, then `Unwritten`, then exit 4.
  - `front_ctl.py:404-406` maps `Unwritten` to exit 4.
- **P1b (mistyped name).**
  - `revoke HOME job-typo2` exits 4: "recorded, not written: job-typo2 is not enrolled  The job's name is revoked in the database, so the front door refuses job-typo2 …".
  - The real job, job-real, is still admitted.
  - The mistyped name is spent for good. A later honest enrolment of `job-typo` gets its certificate, and the front door answers REVOKED at its first use, with nothing said at the console.
- **P1c (wrong key, with A and B both pinned — the rotation window that M-1's rule describes).**
  - `revoke job-a --key B` exits 4. Row B:job-a is (1, True), row A:job-a stays (1, False), and A's job-a is still admitted.
  - At c5c9832 the same command was refused with status 1.
- **P1d (trailing newline).** `JOB_NAME` is `^…$` used with `.match`, so `'job-n\n'` passes. It is revoked under a row of its own, exit 4, and job-n is still admitted.
- **The documented meaning of status 4 is now false in these cases.**
  - README_FRONT.md:166-167 says: "status 4; the front door refuses the job already, and `revoke` given again writes it".
  - For any revocation by name, a second `revoke` never writes anything (P1e).
  - README:162's list of cases ("removed, spoiled, or another job's") leaves out "signed by another key", which the code sends down the same path.
- **Fix options (the author's decision).**
  - Give the case its own exit status, and say plainly in the message that no entry was found and the job may not be the one meant.
  - Or require an explicit `--by-name`.
  - Do not revoke by name when the entry is valid under another pinned key, or say so in the message.
  - Use `fullmatch` for `JOB_NAME`, here and in `front_door`.

**N7-M2. `jobs.json` becomes mode 0600, so a front door under another account reads nothing and admits nobody. Regression; fails closed.** RUN for the mode and the file access; ARGUED for the deployment consequence.
- **Where.**
  - `front_ctl.py:193`: `tempfile.mkstemp` makes the file 0600, and `os.replace` keeps that mode.
  - `front_door.py:104-110`: `read_jobs` turns `PermissionError` into `{}` ("admits nobody") and logs nothing.
- **P2a.** After the console's write, `jobs.json` is 0o600 at fb544a0 and 0o644 at c5c9832 (umask 022).
- **P2b.** The `nobody` account, given the directory by descriptor, gets `PermissionError` on the fb544a0 file and can open the c5c9832 one.
- **Consequence.**
  - README:121-126 ("Who holds what") and :199 describe separate parties, and say that the tests do not show the separation.
  - With the front door under its own account, after the first enrol or revoke every job is answered NOT_ENROLLED, and `record_revocations` sees nothing.
  - Every later console write sets the mode back to 0600, so a manual `chmod` does not last.
  - No test or planted defect can see this, since every party runs under one account.
- **Fix.** `os.fchmod(tfd, 0o644)`, or copy the previous file's mode, before the replace.

== LOW ==

- **L7-1. What is left of M-2 and M-3: `jobs.json` is still read by name, so the revocation by name can be prevented.** RUN: `p2_files.out` P2c and P2e.
  - Where: `front_ctl.py:229-230` (`_current` calls `read_jobs`), and `front_door.py:107` (`read_text` by name, unbounded).
  - **P2c (pipe).** With a pipe at `jobs.json`, CLI `revoke` hangs before recording anything (killed after 10 s, row stays (1, False)). The front door's admit blocks too. When the adversary writes the honest text into the pipe, the blocked admit returns admitted.
  - **P2e (link to `/dev/zero`).** CLI `revoke` under RLIMIT_AS = 768 MB ends with a `MemoryError` traceback after 0.6 s, with no "refused:" line and nothing recorded. `MemoryError` is not caught by `read_jobs`.
  - On the front door, without a memory limit, every request and every look reads `/dev/zero` until the machine runs short of memory (ARGUED; not run). That would hit the database and the other services too. This part predates these commits.
  - Neither case is silent, but both stop revocation for as long as the obstruction stays.
  - Fix: read `jobs.json` through `_plain`-style opening (no link, no blocking, plain file only) with a size limit. Or record the revocation by name before reading the file at all.
- **L7-2. A link at `jobs.json` is followed for reading** (P2d: the outside file is read; the write replaces the link and leaves the outside file untouched). This gives a folder writer nothing it does not already have. RUN.
- **L7-3. Hard link at the log.** A hard link at `enrolment.jsonl` passes `_plain` (`S_ISREG`), and the binding is appended to the outside file (P2g, RUN, same account). With `fs.protected_hardlinks=1` (set here), another account can only link files it owns or can read and write. Informational.
- **L7-4. Writes that are lost or misreported** (ARGUED, predates these commits).
  - The log line is written after the replace (`front_ctl.py:204`). An `os.write` failure there (disk full) means:

  - There is no fsync of the file or the directory.
