== THE QUESTIONS ==

**Q2: can anyone short of the engineer's key get a revoked or superseded binding admitted?**
- **Within one key's row:** no (RUN, P2a to P2c).
  - A revocation is absorbing at any sequence number (the SQL is unchanged).
  - A lower sequence number is STALE, and a second ENROL is CONFLICT.
- **Several pinned keys, or a rotation:** yes, through M-1. It needs a second key's enrolment of the same name after the entry is removed.
- **Signer case or form:** no (RUN, P1c).
  - The signer is not in the signed message, and `bytes.fromhex` accepts upper case, so the signature still verifies under a changed signer field.
  - But the signer must equal a pinned string, and `nameable` needs lower-case hex. With pins [a] or [a, A], both altered copies are unusable, and no upper-case row is made.
  - With only upper-case pins, everything is refused, which fails closed (as before).
- **The console's key against the entry's signer:** consistent. `_current` requires `entry.signer == key.public_hex`, and the new binding's signer is the same, so both name one row.
- **M1 re-record path:** an earlier enrolment's REVOKE of the same name falls on the same row and is re-recorded (P2c). A foreign REVOKE is refused (`p4_cli` a).
- **Changed and lock paths:** a revocation never ends recorded-and-unwritten without a message. The one silent case is a hang through `jobs.tmp` (M-3). The non-silent loss is L-1.
- **admit, sweep and record_revocations ordering:** unchanged apart from the naming. admit's observe before the certificate check only moves the row to the file's signed binding (ARGUED, as in the previous review).
- **CAP-DB:** can deny, not admit (P2g; the SQL is unchanged).
