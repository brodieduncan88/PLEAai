== HIGH ==

**H1''. The realm comes from a file the D16 adversary can write, and the console and the front door both trust it.** RUN: `p1_realm_forgery.out` and `p1b_rerun.out`; all predictions held.

- **Where.**
  - front_state.py:113-154: `read_realm` and `fix_realm` read `HOME/front/realm`.
  - front_ctl.py:132-138: `_realm` returns the file's realm. When the console is given a different one, it is the file's realm that gets used.
  - front_ctl.py:255-257: `revoke` records under that realm.
  - front_door.py:410 with front_state.py:151-154: a start without `--realm` adopts the file.
  - README_FRONT.md:141 says "a later start may leave it out".
- **Who can write the file.** The console must have write access to `HOME/front`, because `_write` uses a temporary file and `os.replace` (front_ctl.py:155). So whoever can put `jobs.json` back can also replace `realm`.
- **P1a: console with no `--realm`, the documented command.**
  - The adversary writes another valid realm into `HOME/front/realm`.
  - The engineer runs revoke. It returns normally, and the CLI exits 0 (P1d) with nothing on stderr.
  - The REVOKE row lands under the forged realm. The real `R:job-x` row stays at seq 1, not revoked.
  - The adversary restores the file and puts back the earlier `jobs.json`. A front door started with the real realm admits the job (`p1a_admitted_after_put_back: True`).
  - The front door reads the realm only at start, so the forged file can stay in place while it runs. An adversary who watches `jobs.json` can revert it before the 30-second look, so this is not limited to a stopped front door.
- **P1b: operator restarts without `--realm`, as the README allows.**
  - The revocation was correctly recorded under R. The adversary forges the file and puts back `jobs.json`.
  - The front door starts under the forged realm and admits the job (`admitted_without_flag: True`).
  - Started with `--realm R`, it refuses (RealmMismatch). That is how deploy_front.py:63 starts it, so that path fails closed.
- **P1c: console given `realm=R`, as deploy_front.py:86 does.**
  - The file is forged to R4. The revocation is recorded under R4 only.
  - The console raises Unrecorded with the text "it was recorded under the front door's own realm", which is false here.
  - After restore and put-back, the job is admitted.
  - At f4c1de6, a console given R recorded under R. So this is a regression for the deploy_front path.
- **The stated limit is inaccurate.** front_state.py:35-38 says the folder writer must also be able to start the front door. P1a needs only write access to the folder.
- **Fix options (the author's decision).**
  - Best: key the record by data the engineer signs. Either use the binding's `cert_sha256`, which all of a job's bindings share, or add `realm` to BINDING_FIELDS and have the front door refuse a binding whose realm differs from its own. A folder writer cannot change signed data.
  - Or: take the realm from operator configuration outside `HOME/front`, make `--realm` mandatory on every start (as at f4c1de6), and have the console prefer a realm it is given, or record under both, over the file.
