# Amendment 15, 20 November 2026

Private working material. Times are UTC.

This is internal work by the author of the code, under the owner's direction. It is not an independent validation.

## What it does

The sandbox of Amendment 12 would not run a check unless the machine's file table (`fs.file-max`) was at least 2^40, a
figure that was never measured, and the machine's table was raised to the largest number the kernel takes to meet it. The
owner asked that so high a limit not be kept without being shown to be needed, and what becomes of the sandbox when the
machine is started again, or has cgroup v2. `DECLARED_AMEND15.md` states the changes, the expected outcomes, the
development work and what stays open.

In short:

- **A limit above the machine's own is needed, and 2^40 is not.** A run can keep files open without descriptors, through
  memory mappings. One run kept about 2.6 million open; this machine starts with a table of 1,644,500.
- **The floor is worked out.** The table must hold twice what four runs can keep open, counted from the machine's limit
  on mappings and the run's own limits: 33,617,920 on this machine, where it was 1,099,511,627,776. Where a process may
  have 1,048,576 mappings, as Ubuntu 24.04 sets it when started in the usual way, the floor is 134,283,776.
- **Four runs at once is the machine's count.** Each run holds one of four locks in `/run/verify-sandbox`, so two
  processes that run checks no longer make eight between them. The count each process kept for itself is taken out.
- **What the machine must give is one list of six, looked at before every run and said**: root, x86-64, cgroup v1 control
  groups, user namespaces, the folder of places, the file table. Where one is not met the check is not run, the verdict is
  UNKNOWN, and the words say which and why. A machine with cgroup v2 only is refused in those words.
- **An operator can ask**: `python3 verify/sandbox.py --prerequisites`, which makes no run and changes nothing.
- **Nothing raises the table.** A machine started again with its own table runs no check and says why. Keeping the
  setting is the operator's step and has not been made on this machine.

Only `verify/sandbox.py`, `verify/README.md` and `tests/verify_tests.py` are changed. The gateway is not.

## What changed on the way

The code went through three forms, and two independent reviews, each by a separate agent that read the code and ran no
test. Neither made a finding of high weight; each made findings of medium weight in the form before it.

The first form counted a run's files as its processes times its mappings and descriptors, and four runs for each process
of the service. The first review found that the file table is the machine's while that count was each process's; that
the limit on mappings is sixteen times higher on Ubuntu 24.04 as usually started than on this machine, which would have
made the floor 537 million there and left an operator who followed the readme with every run refused; and that
shared-memory segments, a process's own program and one mapping more are files the count left out. The second form
counts runs for the machine, bounds a process's mappings by the pages its memory limit allows, and adds the files left
out.

The second review found that the test of the count used the machine's own places, so that anything else using them could
change its result; that the folder of places was not in the list; and that a run could wait twice. It also found two
things that are not repaired and stay open, below. The third form is the code declared.

Passes of deliberate defects were made on each form: 20 of 21 caught on the first, 33 of 34 on the third, the control
passing each time. The one not caught by a check is the same in both: with a table exactly at the floor refused, nothing
runs on this machine, whose table is at the floor, and R29 stops with an error, having failed no check.

**One test failed in development and was not explained.** `w4_service_crash`, one of the four whole-gate tests, failed
once: in one of its 18 cases a retry, after the service had been killed, timed out. It runs none of the code changed
here. It passed in six runs after that. It is not one of the two official commands.

The third form's changes were read only by their author.

## What stays open

The declaration's "What stays open" section is the full list. The main items are:

- **A place is let go when its service dies; the run's files may not be.** A run left frozen by a killed service keeps
  what it holds until a later run sweeps it, and a fifth run can begin beside it. The margin of two covers one such; it
  is not counted.
- **Runs are counted together only by services that share one /run.** Services in containers of their own on one kernel
  are not.
- **The count of what one run can hold is an argument.** It was reviewed twice, and rests in part on what the reviewers
  know of the kernel, not on a reading of this kernel's source. The one run measured stopped well below it.
- **Where many mappings are allowed the floor is high**: 134 million on Ubuntu 24.04 as usually started. Lowering it
  would mean allowing a run fewer processes or less memory.
- **The setting is made by hand and lost at each start of the machine.** The number to set is the one the operator's
  command gives; an earlier form of this work gave 33,584,128, which is now below the floor.
- **The operator's command makes no run.** It can say all six are met on a machine where a run then fails, closed: for
  one, where user namespaces are forbidden to unprivileged users by another setting.
- **cgroup v2 is not supported**, and was not tested on a real machine: only a file that reads as one.
- **A start of the machine was not made on purpose.** It happened several times; each time the sandbox refused until the
  table was raised.
