## Findings

**CRITICAL:** none. **HIGH:** none. **MEDIUM:** none.

**L-1. The README's procedure for replacing a key is incomplete.** `verify/README_FRONT.md:146-149`. ARGUED, partly RUN (probe D).
- The statement that rotation is unsupported is accurate. The steps for "should a key have to be replaced" leave out three things:
  - **New baselines are needed.** Enrolling under the new key needs a baseline signed by that key whose card names it:
    - the console's `_envelope` pins the console's own key (`front_ctl.py:98-105`);
    - `load_envelope` requires the signer to equal `card.responsible_engineer.key` (`verify_record.py:79-80`).
  - Each requirement therefore has to be baselined again. That gives a new baseline hash, and so a new root and budget that must be provisioned.
  - **The gate host needs the new key.** It pins engineer keys separately, through `VERIFY_ENGINEER_KEYS` (`verify_tools.py:49`, set in `deploy.py:85`).
  - **The revocations must be recorded before the switch.** Probe D: a front door pinned to key B returns `usable()` False for key A's entries, and `record_revocations()` returns 0 without touching the database.
    - So a revocation under A that the console could not record is never recorded while B is pinned, at start or on the look.
    - It would become undoable (by putting the earlier binding back) if A were ever pinned again.
- Scenario: an operator follows the README and is refused at the console with "no baseline … signed by this engineer is held". Nothing fails open.

**L-2. In F39's process check, "binds no port" cannot fail.** `tests/verify_front_tests.py:2165`, `:2179`. ARGUED.
