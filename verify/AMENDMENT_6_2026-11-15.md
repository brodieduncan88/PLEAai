# Amendment 6: a notice for a made-up hash is kept out of a real engineer's inbox

15 November 2026. Private working material. Internal evidence: written, run and checked by the same party.

This amends `DECLARED_AMEND2.md`, which lists the fault under "What stays open", and the declarations after it. None of
them is changed. `DECLARED_AMEND6.md`, committed before the runs reported here, says what was changed, what each test was
expected to show and what was done in development.

## Summary

1. **What was wrong.** The engineer's inbox is named by the first 64 bits of the baseline hash, and the gate's tool
   accepts a request naming any hash. Through the first client, a caller who copied the first 16 digits of a real
   baseline's hash could put notices that "no usable baseline is held", with a design of its choosing, into that
   engineer's inbox. No verdict, record or status was wrong because of it.
2. **The repair.** The inbox is made with its baseline and holds the baseline's full hash. A notice goes to an inbox only
   for the exact hash it holds, or for a hash whose baseline folder the service holds; any other notice is kept in
   `inbox/unclaimed/<the full hash>/`, in no engineer's inbox, and says it is addressed to no engineer.
3. **The tests, on the one official run of each file:** first plug-in 19 of 19 tests, 106 of 106 checks; front door
   21 of 21 tests, 110 of 110 checks. R19 is new.
4. **Planted defects.** Against the tests as declared, 34 of 34 planted defects were caught.
5. **What this does not show.** Nobody outside has reviewed it; the reviews were made by AI agents working for the party
   that wrote the code. Everything ran on one machine.

## Putting the repair into use

- The gate host loads the tool when it starts, so it has to be started again, on the same state file.
- A baseline made before this amendment has an inbox with no claim. The gate's tool writes the claim of every baseline
  it holds when it starts, so starting it again is enough.
- Notices already written are not moved.
